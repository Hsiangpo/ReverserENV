# param-encryptor · 请求传输与状态证据指南

> 仅在算法已定位、字节对拍与业务结果不一致时按需加载。这里提供取证维度，不预设某厂商使用哪些检测项，也不提供通用“模拟人类”参数栈。
> 跨层定位由 `web-reverse-master` 统筹；本 Skill 负责已知算法与请求字段。完整状态机见 [协议与状态指南](../../web-reverse-master/references/14-risk-protocol-and-state.md)，产品公开能力见 [厂商参考](../../web-reverse-master/references/15-vendor-capability-reference.md)。

## 1. 先固定边界和对照

记录 SDK/脚本 hash、客户端与依赖版本、目标接口、采样时间、当前 session、原版对照及业务判官。每个观察注明“官方文档 / 当前实测 / 历史个案 / 待验证”。

- 字节对拍只证明指定输入和熵源下的算法结果；请求被接受还取决于已证实的上游状态、协议顺序及业务条件。
- 请求失败不能单独证明 TLS、指纹、Cookie 或算法有问题。先保留失败响应和原版同环境对照，再选一个变量实验。
- Cookie/token 的存在、长度、格式和 HTTP 200 都不代替最终业务 schema、错误码和预期结果。
- 不向真实 payload 添加没有来源的 session 年龄、人格、速度、随机时间戳或“反检测”字段。研究 harness 的调度/观测信息保存在本地。

## 2. TLS 与 HTTP 的传输取证

可能需要比较的维度取决于实际调用链：

| 层 | 观察内容 | 证据与边界 |
|---|---|---|
| TLS | 协议版本、ClientHello、扩展、ALPN、复用/恢复 | 使用可控服务端日志或授权抓包；JA3/JA4 是摘要，不是浏览器身份或业务接受证明 |
| HTTP/1.1 | 实际发送的 header 名称、值、顺序、大小写、连接语义 | 比较线上字节，不能只看 Python 容器或 DevTools 显示 |
| HTTP/2 | 协商结果、SETTINGS、伪头部、普通 header、连接与流复用 | 与 HTTP/1.1 分开建样本；不得把 `Connection` 等连接专用字段塞入 HTTP/2 |
| HTTP/3 | QUIC/HTTP/3 协商、连接与流行为 | 只有目标实际使用且已采集时才纳入；不从 HTTP/2 模板推断 |
| 上下文 | UA、UA-CH、Fetch Metadata、语言、平台与页面来源 | 检查同一真实客户端的值及生成条件，不能用固定“正确设备值”替代 |

Python 3.10 的普通 `dict` 保持插入顺序；`requests` 不能概括为“按字母序发送”。最终 header 可能被 Session、适配器、HTTP 库、代理或协议编码重组，必须观察实际发送结果。DevTools 的排序视图不是线序证据。

`requests`、`curl_cffi` 或其他客户端按已证实的缺口选择，不强制某一个库。使用 impersonation 时记录库版本、实际支持的 profile、UA/UA-CH 和协商结果；profile 名称不证明已逐项对齐，更不保证服务端接受。不要固定要求某个 Chrome 主版本，也不要把 JA3 原始参数串误称为 hash。

## 3. 时钟、nonce 与重放窗口

先确认时间戳的生成位置、单位、舍入方式、是否参与签名、TTL 与服务端容差，再决定是否需要校时。

- 保存本地发送/接收时间、RTT、原始服务端时间字段及来源。
- HTTP `Date` 常只有秒级精度，且可能由边缘节点生成；不能据此声称毫秒级同步或得知源站校验时钟。
- RTT 中点只是偏移估计，需注明网络不对称、缓存、排队和时间量化带来的误差；多次样本或滤波不会消除来源错误。
- 不默认对签名时间戳添加随机抖动。固定熵源用于离线复现，在线生成按已确认算法执行。
- nonce、一次性 token 的重用/消费规则从原版流程或受控对照确认，不从重复失败猜测。

## 4. Cookie、票据与会话生命周期

每个状态值至少记录：

| 字段 | 要回答的问题 |
|---|---|
| 签发者与入口 | 页面本地生成、上游 `Set-Cookie`、响应头还是 JSON 字段？ |
| 消费方 | 哪个请求/后端验证它；前端得到 token 后是否还有验证调用？ |
| 作用域 | domain/path、Secure、HttpOnly、SameSite、分区或应用存储位置？ |
| 状态迁移 | 未签发、已签发、待验证、已接受、已消费、失效、刷新分别由什么响应证明？ |
| 生命周期/绑定 | TTL、账号、设备、IP、UA、TLS 或请求内容中哪些已有单变量证据，哪些未知？ |
| 结果 | 是否仅通过挑战、是否已通过目标业务；对应响应与日志索引？ |

保存原现场后再做刷新/换值实验。不把 403/429 自动认作“废票”，不把某个 Cookie 后缀当所有站点的成功标志，不把历史同 IP/UA/TLS 复用经历升级成全局绑定定律。

从普通上游 HTTP 获取透传值可以是纯协议链的一环，但不是离线纯算；从真实浏览器取得值必须明示 oracle 依赖。不要用历史成功 Cookie 填平未解析字段。

## 5. 请求顺序、速率和行为

先从真实 initiator、调用栈、请求/响应和 token 消费关系建立依赖图。不要机械添加“先首页、再 JS、再 token”的通用序列。

- 将协议依赖与时间相关性分开：A 先发生不证明 B 必须依赖 A。
- 每条边注明依赖字段、获取位置、可重试性、幂等性和失败时保留的状态。
- 调度遵守授权速率和服务器反馈；并发=1可以是验证约束，不代表已查明厂商阈值。
- 人类请求间隔没有可直接套用到所有业务的固定 Weibull 或其他分布。若研究统计模型，记录授权数据集、动作类别、拟合方法、检验和不确定性。
- 不默认轮换住宅代理、账号或设备，也不把请求间隔随机化作为有效性的证明。

## 6. 最小区分实验与停止条件

每次实验只改变一个已记录维度，并提前写好可区分的预期结果。输出可以采用：

| 假设 | 原版对照 | 唯一改动 | 实际业务结果 | 支持/排除范围 | 下一步 |
|---|---|---|---|---|---|

同一请求同字节最多总计 3 次（含首次）；任一次出现漂移或随量降级就停止同字节重发。达到线上停止条件后做原版对照、全量流量 diff 或离线分析，不能以换 profile、换代理、清 Cookie 的循环替代归因。

算法字节仍不一致时回到第一个不同的中间值；字节一致但业务拒绝时冻结已验证算法，由 master 结合完整状态机继续定位。达到已约定止损线后，记录未解字段、已排除假设、停止原因及可交付边界；不得按状态码自动改走浏览器 Cookie 路线。
